# Argus 项目文档 V4.1

> Argus 是一个 **RAG 知识库平台** 的教学项目，从零搭建，逐步迭代。
> V4.1 在 V4.0（AI 助手）和 V3.0（知识问答）的基础上，为 QA 模块补充了**问答记录持久化**和**chunk 证据链结构化**，
> 使问答结果可追溯、可复盘，证据来源可解释、可审视。

---

## 一、项目概述

### 1.1 V4.1 定位

V3.0 实现了"文档上传 → 自动解析索引 → 混合检索 → AI 生成回答"的完整问答闭环，但存在两个缺口：

1. **问答无痕**：每次问答的结果（回答正文、引用来源、证据充分度、Token 用量）在请求结束后即消失，无法事后回溯。用户想知道"上次那个问题的回答里引用了哪些文档"时无从查起。
2. **证据黑盒**：检索返回的文档切片以纯文本拼接方式注入 LLM，前端只能看到最终回答和简单的引用列表，无法解释"哪些切片被检索到？它们来自哪个通道（向量/关键词）？评分如何？覆盖了答案的哪些方面？"

V4.1 补上了这两个缺口：

- **问答记录持久化**：每次同步/流式问答完成后，自动将问题、回答、证据等级、Token 用量和引用快照落库。提供问答历史的分页查询、详情查看和删除接口。流式 SSE 回答在 `done` 阶段附带持久化生成的 `recordId`，前端可据此关联问答记录。
- **chunk 证据链结构化**：检索引擎在组装证据 Document 时，为每份证据携带完整的追溯元数据（文档 ID、切片范围、向量/关键词/混合评分、检索来源），并在 API 响应中提供按文档聚合的 `EvidenceOverview`（证据覆盖概览）。前端据此渲染"证据链"面板，展示每条证据的切片位置、评分柱状图和来源通道。

V4.1 的核心创新集中在**可观测性侧**：让每一次 RAG 问答的"输入端（检索了什么）"和"输出端（回答了了什么、花了多少 Token）"都变得可见、可查、可复盘。

## 四、数据库设计

### 4.1 概述

**V4.1 新增了 2 张数据库表**，用于持久化 QA 问答记录及其引用快照。

| 表名 | 用途 | 核心字段 |
|------|------|---------|
| `qa_records` | 问答记录主表 | id, user_id, group_id, question, answer, answered, evidence_level, citation_count, prompt_tokens, completion_tokens, total_tokens, latency_ms, model_name, endpoint, success |
| `qa_record_citations` | 引用快照表 | id, qa_record_id, document_id, chunk_id, chunk_index, start/end_chunk_index, file_name, score, retrieval_source, vector_score, keyword_score, hybrid_score, snippet |

### 4.2 qa_records（问答记录表）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | BIGSERIAL | PK | 问答记录主键，自增 |
| user_id | BIGINT | NOT NULL | 提问用户 ID，关联 `users.id` |
| group_id | BIGINT | NOT NULL | 问答发生的知识库群组 ID |
| question | TEXT | NOT NULL | 用户原始问题 |
| answer | TEXT | NULL | 模型生成的回答正文，拒答或失败时可为空 |
| answered | BOOLEAN | NOT NULL | 是否成功回答了问题 |
| reason_code | VARCHAR(64) | NULL | 拒答或失败原因编码（如 INSUFFICIENT_EVIDENCE） |
| reason_message | TEXT | NULL | 拒答或失败原因说明 |
| evidence_level | VARCHAR(32) | NULL | 证据充分性等级：NONE / WEAK / PARTIAL / SUFFICIENT |
| citation_count | INTEGER | NOT NULL DEFAULT 0 | 保存的引用快照数量 |
| prompt_tokens | INTEGER | NULL | 输入 token 数 |
| completion_tokens | INTEGER | NULL | 输出 token 数 |
| total_tokens | INTEGER | NULL | 总 token 数 |
| is_estimated | BOOLEAN | NOT NULL DEFAULT false | token 用量是否为估算值（流式场景可能无法获取精确 usage） |
| latency_ms | BIGINT | NULL | 本次问答耗时，单位毫秒 |
| model_name | VARCHAR(64) | NULL | 调用的大模型名称 |
| endpoint | VARCHAR(64) | NULL | 触发记录的接口端点（QA_ASK / QA_STREAM_ASK） |
| success | BOOLEAN | NOT NULL | 本次问答流程是否成功完成（拒答为 false） |
| error_message | TEXT | NULL | 系统异常信息，业务拒答时通常为空 |
| created_at | TIMESTAMP | NOT NULL | 记录创建时间 |

设计要点：
- `answered` 和 `success` 是两个独立维度：`answered=true, success=true` 表示正常回答；`answered=false, success=true` 表示业务拒答（证据不足）；`answered=false, success=false` 表示系统异常。
- `endpoint` 区分同步（QA_ASK）和流式（QA_STREAM_ASK）两种调用路径，便于运维统计。
- `evidence_level` 为枚举字符串，与 `EvidenceLevel` 枚举的 `name()` 对应。
- 所有查询均通过 `visiblePredicate` 做可见性过滤，确保数据隔离。

### 4.3 qa_record_citations（引用快照表）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | BIGSERIAL | PK | 引用快照主键，自增 |
| qa_record_id | BIGINT | NOT NULL | 所属 QA 记录 ID，关联 `qa_records.id` |
| document_id | BIGINT | NULL | 来源文档 ID |
| document_version_id | BIGINT | NULL | 来源文档版本 ID（当前未启用版本管理） |
| chunk_id | BIGINT | NULL | 来源切片 ID |
| chunk_index | INTEGER | NULL | 切片在文档中的序号（从 0 开始） |
| start_chunk_index | INTEGER | NULL | 合并证据片段的起始切片序号 |
| end_chunk_index | INTEGER | NULL | 合并证据片段的结束切片序号 |
| file_name | VARCHAR(512) | NOT NULL | 来源文件名 |
| score | DOUBLE PRECISION | NULL | 最终相关性得分（RRF 归一化后） |
| retrieval_source | VARCHAR(16) | NULL | 检索来源类型：VECTOR / KEYWORD / BOTH |
| vector_score | DOUBLE PRECISION | NULL | 向量检索原始得分 |
| keyword_score | DOUBLE PRECISION | NULL | 关键词检索原始得分 |
| hybrid_score | DOUBLE PRECISION | NULL | 混合检索融合得分（RRF 原始累加值） |
| snippet | TEXT | NULL | 回答时使用的证据文本快照（≤1200 字符） |
| created_at | TIMESTAMP | NOT NULL | 快照创建时间 |

设计要点：
- 引用快照是**回答时刻的证据截面**——即使后续文档被修改或删除，快照中的 `snippet` 和 `chunk_index` 仍保留当时的证据内容。
- `start_chunk_index` 和 `end_chunk_index` 记录了邻居窗口扩展后的完整切片范围，展示给用户的是"模型实际看到了哪些内容"。
- `vector_score`、`keyword_score`、`hybrid_score` 三个维度的评分同时保存，便于事后分析检索质量。
- `snippet` 通过正则归一化（合并空白字符）后截断至 1200 字符，平衡信息完整性和存储开销。
- `retrieval_source` 标记每个切片来自哪个检索通道——BOTH 表示双通道均命中（置信度最高），单一通道命中则标记为 VECTOR 或 KEYWORD。

### 4.4 可见性过滤设计

QA 历史查询的核心安全机制是 `visiblePredicate`——一个可复用的 MyBatis SQL 片段，在 `selectVisibleRecords`、`countVisibleRecords` 和 `selectVisibleRecord` 三处引用：

```sql
<choose>
    <when test="systemAdmin">
        1 = 1  <!-- 系统管理员可见全部记录 -->
    </when>
    <otherwise>
        EXISTS (
            SELECT 1 FROM group_memberships gm
            WHERE gm.group_id = r.group_id
              AND gm.user_id = #{currentUserId}
              AND (r.user_id = #{currentUserId} OR gm.role = 'OWNER')
        )
    </otherwise>
</choose>
```

规则：
- **系统管理员**：可见所有 QA 记录。
- **普通用户**：只能看到自己所属群组的 QA 记录，且在该群组中要么是记录提问者本人（`r.user_id = #{currentUserId}`），要么是该群组的 OWNER。

这样确保了一个群组的普通成员能看到 OWNER 的所有问答记录（便于团队知识共享），但不能看到其他群组的记录。

### 4.5 索引建议

| 索引 | 所在表 | 用途 |
|------|--------|------|
| `(user_id, group_id, created_at)` 复合索引 | `qa_records` | 用户按群组查询历史记录 |
| `(group_id, created_at DESC)` 复合索引 | `qa_records` | 群组维度的时间序列表查询 |
| `qa_record_id` 索引 | `qa_record_citations` | 按记录 ID 查询引用快照（详情页） |
| `qa_record_id` 唯一索引 | `qa_record_citations` | 级联删除时的快速定位 |

**响应字段说明（V4.1 新增）**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `evidenceOverview` | object | 证据覆盖概览，为 null 时表示无检索证据 |
| `evidenceOverview.documentCount` | int | 本次回答涉及的文档数量 |
| `evidenceOverview.evidenceCount` | int | 本次回答使用的证据切片数量 |
| `evidenceOverview.coverageMode` | string | 检索覆盖模式：RELEVANCE_ONLY（按相关性取 topK）或 DOCUMENT_COVERAGE（跨文档覆盖） |
| `evidenceOverview.groups` | array | 按文档聚合的证据组 |
| `evidenceOverview.groups[].retrievalSources` | string[] | 该文档证据的检索来源（VECTOR / KEYWORD / BOTH） |
| `evidenceOverview.groups[].snippets[].startChunkIndex` | int | 邻居窗口扩展后的起始切片序号 |
| `evidenceOverview.groups[].snippets[].endChunkIndex` | int | 邻居窗口扩展后的结束切片序号 |
| `evidenceOverview.groups[].snippets[].retrievalSource` | string | 该条证据的检索来源通道 |

## 八、枚举扩展

### 8.1 V4.1 新增/增强枚举

V4.1 未新增 Java 枚举类型，但增强了现有枚举的使用场景。

| 枚举 | 新增使用场景 | 说明 |
|------|-------------|------|
| `EvidenceLevel` | 持久化到 `qa_records.evidence_level` 字段 | 以 `name()` 字符串形式存储 |
| `LlmEndpoint.QA_ASK` | QaService 持久化时传入 | 标记同步问答端点 |
| `LlmEndpoint.QA_STREAM_ASK` | QaService 持久化时传入 | 标记流式问答端点 |

### 8.2 证据覆盖模式（字符串常量）

在 `EvidenceOverview.coverageMode` 中使用，不是 Java 枚举，而是运行时字符串：

| 值 | 触发条件 | 行为 |
|----|---------|------|
| `RELEVANCE_ONLY` | 默认模式 | 按 RRF 评分取 topK 候选切片，不考虑文档覆盖 |
| `DOCUMENT_COVERAGE` | 用户问题中包含"每个文档""所有文档"等关键词 | 优先确保不同文档各至少有一条证据，避免单个高相关文档独占 topK |
| `HISTORY_SNAPSHOT` | 从数据库引用快照重建 EvidenceOverview | 标记该概览来自历史数据而非实时检索 |

### 9.2 数据库初始化

V4.1 新增了 2 张表，需要执行以下 DDL：

```sql
-- QA 问答记录主表
CREATE TABLE qa_records (
    id BIGSERIAL PRIMARY KEY,
    user_id BIGINT NOT NULL,
    group_id BIGINT NOT NULL,
    question TEXT NOT NULL,
    answer TEXT,
    answered BOOLEAN NOT NULL,
    reason_code VARCHAR(64),
    reason_message TEXT,
    evidence_level VARCHAR(32),
    citation_count INTEGER NOT NULL DEFAULT 0,
    prompt_tokens INTEGER,
    completion_tokens INTEGER,
    total_tokens INTEGER,
    is_estimated BOOLEAN NOT NULL DEFAULT false,
    latency_ms BIGINT,
    model_name VARCHAR(64),
    endpoint VARCHAR(64),
    success BOOLEAN NOT NULL,
    error_message TEXT,
    created_at TIMESTAMP NOT NULL DEFAULT NOW()
);

-- QA 引用快照表
CREATE TABLE qa_record_citations (
    id BIGSERIAL PRIMARY KEY,
    qa_record_id BIGINT NOT NULL REFERENCES qa_records(id) ON DELETE CASCADE,
    document_id BIGINT,
    document_version_id BIGINT,
    chunk_id BIGINT,
    chunk_index INTEGER,
    start_chunk_index INTEGER,
    end_chunk_index INTEGER,
    file_name VARCHAR(512) NOT NULL,
    score DOUBLE PRECISION,
    retrieval_source VARCHAR(16),
    vector_score DOUBLE PRECISION,
    keyword_score DOUBLE PRECISION,
    hybrid_score DOUBLE PRECISION,
    snippet TEXT,
    created_at TIMESTAMP NOT NULL DEFAULT NOW()
);

-- 推荐索引
CREATE INDEX idx_qa_records_user_group_time ON qa_records(user_id, group_id, created_at DESC);
CREATE INDEX idx_qa_records_group_time ON qa_records(group_id, created_at DESC);
CREATE INDEX idx_qa_citations_record_id ON qa_record_citations(qa_record_id);
```
