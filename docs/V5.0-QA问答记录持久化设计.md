# V5.0 QA 问答记录持久化设计

## 1. 背景

当前 Argus 的知识库问答模块已经具备完整的 RAG 流程：权限校验、查询规划、混合检索、证据评估、LLM 生成、引用溯源和 LLM 用量统计。但 QA 问答结果本身没有持久化。

现状如下：

- `QaService` 负责 `/api/qa/ask` 和 `/api/qa/stream-ask` 的入口编排，只记录 `llm_usage_records`。
- `QaChatService` 返回 `AskQuestionResponse`，其中包含 `answered`、`answer`、`reasonCode`、`reasonMessage` 和 `citations`。
- 前端 `useQaSessions.ts` 使用内存态 `ref([])` 维护 QA 会话，刷新页面后历史记录丢失。
- `assistant` 模块已经有 `assistant_sessions`、`assistant_messages`、`assistant_session_contexts`，但 QA 模块没有对应的问答记录表。

这会限制后续知识治理能力：

- 无法统计高频问题、拒答率、证据不足率。
- 无法分析哪些文档经常被引用，哪些文档从未命中。
- 无法把用户反馈关联到一次具体问答。
- 后续文档版本管理上线后，历史回答无法追溯当时引用的文档版本。

## 2. 目标

本设计目标是为 QA 模块增加轻量级问答记录持久化，保存每一次知识库问答的关键事实和引用证据。

核心目标：

- 保存用户问题、系统回答、拒答原因和引用来源。
- 支持用户查看自己的 QA 历史。
- 支持群组 Owner / Manager / Admin 后续做质量分析。
- 为答案反馈、知识库质量看板、文档版本引用打基础。
- 不改变当前 QA 的“单次知识问答”定位，不把 QA 模块改造成完整多轮 Assistant。

非目标：

- 不在本阶段实现答案反馈。
- 不在本阶段实现质量看板。
- 不在本阶段实现文档版本管理。
- 不在本阶段引入 QA 短期记忆或多轮上下文。
- 不把 QA 历史和 Assistant 会话合并。

## 3. 用户故事

### 3.1 普通用户

作为普通用户，我希望刷新页面后仍能看到自己曾经问过的问题和答案，方便复查之前的引用来源。

验收点：

- 用户可以查看自己的 QA 历史列表。
- 用户只能查看自己有权限访问的群组内历史。
- 历史详情包含问题、回答、引用、拒答原因和创建时间。

### 3.2 群组管理者

作为群组 Owner / Manager，我希望后续能够分析本群组的问答质量，知道哪些问题经常答不上来、哪些文档经常被引用。

验收点：

- 每条 QA 记录必须带 `group_id`。
- 每条引用必须保存 `document_id`、`chunk_id` 和分数。
- 拒答记录也必须入库。

### 3.3 系统管理员

作为系统管理员，我希望 QA 记录能与 LLM 用量记录关联或至少在口径上可对齐，方便后续做成本、使用量和质量分析。

验收点：

- QA 记录保存 token、耗时、模型名等摘要字段。
- 后续可选择通过 `qa_record_id` 反向关联 `llm_usage_records`。

## 4. 数据模型设计

### 4.1 `qa_records`

用于保存一次完整的 QA 请求结果。一次请求对应一条记录，无论成功回答、拒答、格式错误或系统异常，都应尽量记录。

建议 DDL：

```sql
CREATE TABLE IF NOT EXISTS qa_records (
    id                  BIGSERIAL       PRIMARY KEY,
    user_id             BIGINT          NOT NULL,
    group_id            BIGINT          NOT NULL,
    question            TEXT            NOT NULL,
    answer              TEXT,
    answered            BOOLEAN         NOT NULL DEFAULT FALSE,
    reason_code         VARCHAR(64),
    reason_message      TEXT,
    evidence_level      VARCHAR(32),
    citation_count      INT             NOT NULL DEFAULT 0,
    prompt_tokens       INT             NOT NULL DEFAULT 0,
    completion_tokens   INT             NOT NULL DEFAULT 0,
    total_tokens        INT             NOT NULL DEFAULT 0,
    is_estimated        BOOLEAN         NOT NULL DEFAULT FALSE,
    latency_ms          BIGINT          NOT NULL DEFAULT 0,
    model_name          VARCHAR(64),
    endpoint            VARCHAR(64)     NOT NULL,
    success             BOOLEAN         NOT NULL DEFAULT TRUE,
    error_message       TEXT,
    created_at          TIMESTAMP       NOT NULL DEFAULT now(),

    CONSTRAINT fk_qa_record_user  FOREIGN KEY (user_id)  REFERENCES users (id),
    CONSTRAINT fk_qa_record_group FOREIGN KEY (group_id) REFERENCES groups (id)
);
```

字段说明：

| 字段 | 说明 |
|---|---|
| `user_id` | 提问用户 ID |
| `group_id` | 问答所属知识库群组 |
| `question` | 用户原始问题 |
| `answer` | AI 回答正文；拒答或异常时可为空 |
| `answered` | 是否成功回答 |
| `reason_code` | 拒答或失败原因编码，如 `INSUFFICIENT_EVIDENCE` |
| `reason_message` | 拒答或失败原因说明 |
| `evidence_level` | 检索证据充分度，如 `NONE`、`WEAK`、`PARTIAL`、`SUFFICIENT` |
| `citation_count` | 引用数量，用于列表页快速展示 |
| `prompt_tokens` | 输入 token 数 |
| `completion_tokens` | 输出 token 数 |
| `total_tokens` | 总 token 数 |
| `is_estimated` | token 是否为估算值，流式接口可能为 true |
| `latency_ms` | 端到端耗时 |
| `model_name` | 使用模型，如 `qwen-plus` |
| `endpoint` | 来源接口，如 `qa/ask`、`qa/stream-ask` |
| `success` | 请求是否完成业务处理；业务拒答仍属于 success=true |
| `error_message` | 系统异常信息 |
| `created_at` | 创建时间 |

建议索引：

```sql
CREATE INDEX IF NOT EXISTS idx_qa_records_user_created
    ON qa_records (user_id, created_at DESC);

CREATE INDEX IF NOT EXISTS idx_qa_records_group_created
    ON qa_records (group_id, created_at DESC);

CREATE INDEX IF NOT EXISTS idx_qa_records_group_answered_created
    ON qa_records (group_id, answered, created_at DESC);

CREATE INDEX IF NOT EXISTS idx_qa_records_reason_created
    ON qa_records (reason_code, created_at DESC);
```

### 4.2 `qa_record_citations`

用于保存一次 QA 回答引用的文档切片。当前先保存文档和 chunk 信息，预留 `document_version_id` 以支持后续文档版本管理。

建议 DDL：

```sql
CREATE TABLE IF NOT EXISTS qa_record_citations (
    id                  BIGSERIAL       PRIMARY KEY,
    qa_record_id        BIGINT          NOT NULL,
    document_id         BIGINT,
    document_version_id BIGINT,
    chunk_id            BIGINT,
    chunk_index         INT,
    file_name           VARCHAR(512),
    score               DOUBLE PRECISION NOT NULL DEFAULT 0,
    snippet             TEXT,
    created_at          TIMESTAMP       NOT NULL DEFAULT now(),

    CONSTRAINT fk_qa_citation_record FOREIGN KEY (qa_record_id) REFERENCES qa_records (id) ON DELETE CASCADE
);
```

字段说明：

| 字段 | 说明 |
|---|---|
| `qa_record_id` | 所属 QA 记录 |
| `document_id` | 来源文档 ID |
| `document_version_id` | 来源文档版本 ID，当前可为空，后续版本管理上线后填充 |
| `chunk_id` | 来源切片 ID |
| `chunk_index` | 切片在文档中的序号 |
| `file_name` | 回答时展示的来源文件名快照 |
| `score` | 检索相关性分数 |
| `snippet` | 引用摘要或片段快照 |

建议索引：

```sql
CREATE INDEX IF NOT EXISTS idx_qa_citations_record
    ON qa_record_citations (qa_record_id);

CREATE INDEX IF NOT EXISTS idx_qa_citations_document_created
    ON qa_record_citations (document_id, created_at DESC);

CREATE INDEX IF NOT EXISTS idx_qa_citations_chunk
    ON qa_record_citations (chunk_id);
```

## 5. 后端设计

### 5.1 包结构

沿用现有模块组织方式，在 `com.argus.rag.qa` 下新增：

```text
qa/
├── mapper/
│   ├── QaRecordMapper.java
│   └── QaRecordCitationMapper.java
├── model/
│   ├── entity/
│   │   ├── QaRecordEntity.java
│   │   └── QaRecordCitationEntity.java
│   ├── dto/
│   │   └── QaHistoryQueryRequest.java
│   └── vo/
│       ├── QaRecordDetailVO.java
│       └── QaRecordListItemVO.java
└── service/
    ├── QaRecordService.java
    └── QaRecordPersistenceService.java
```

职责划分：

| 类 | 职责 |
|---|---|
| `QaRecordEntity` | 映射 `qa_records` |
| `QaRecordCitationEntity` | 映射 `qa_record_citations` |
| `QaRecordMapper` | 插入和查询 QA 记录 |
| `QaRecordCitationMapper` | 批量插入和查询引用 |
| `QaRecordPersistenceService` | 从 `AskQuestionResponse` 和 usage 组装并落库 |
| `QaRecordService` | 面向 Controller 的历史查询、详情查询 |

### 5.2 与现有 `QaService` 的集成

当前同步问答流程：

```text
QaController.askQuestion
  -> QaService.ask
    -> groupMembershipService.requireGroupReadable
    -> qaChatService.askWithUsage
    -> recordUsage
    -> return result.response
```

调整后：

```text
QaController.askQuestion
  -> QaService.ask
    -> groupMembershipService.requireGroupReadable
    -> qaChatService.askWithUsage
    -> qaRecordPersistenceService.save(...)
    -> recordUsage
    -> return response with qaRecordId
```

建议在 `AskQuestionResponse` 中新增可选字段：

```java
Long recordId
```

原因：

- 前端可以用 `recordId` 展示历史详情。
- 后续答案反馈可以直接提交 `qaRecordId`。
- 不破坏已有字段语义；旧客户端忽略新字段即可。

### 5.3 调整 `QaChatService.AskResult`

当前 `AskResult` 只包含：

```java
public record AskResult(AskQuestionResponse response, UsageInfo usage) {}
```

建议扩展为：

```java
public record AskResult(
        AskQuestionResponse response,
        UsageInfo usage,
        EvidenceLevel evidenceLevel
) {}
```

如果后续还需要保存查询规划结果，可继续扩展：

```java
QueryPlanStrategy queryPlanStrategy
List<String> plannedQueries
```

本阶段先保存 `evidenceLevel` 即可。

### 5.4 流式问答持久化策略

当前 `/api/qa/stream-ask` 返回 `StreamContext(tokenStream, documents)`，Controller 在 `doOnComplete` 后发送 citations。

流式落库需要处理两个问题：

- token 是逐步返回的，需要拼接完整 answer。
- 用户可能中断连接，回答可能不完整。

建议策略：

1. 在 `QaService.askStream` 返回的上下文中增加落库所需信息。
2. 在 token 流 `doOnNext` 中累积 answer 文本。
3. 在 `doOnComplete` 中保存完整记录，`success=true`。
4. 在 `doOnError` 中保存失败记录，`success=false`，`error_message` 保存异常原因。
5. 如果客户端主动断开，保留已生成文本，记录 `success=false`，`reason_code=STREAM_INTERRUPTED`。

为了避免 Controller 承担过多业务逻辑，建议把流式保存封装到 `QaService` 或 `QaRecordPersistenceService`。

可选实现形态：

```java
public record StreamContext(
        Flux<String> tokenStream,
        List<Document> documents,
        EvidenceLevel evidenceLevel,
        Long userId,
        Long groupId,
        String question
) {}
```

但更推荐新增内部包装服务，让 Controller 仍只负责 SSE 输出。

## 6. API 设计

### 6.1 返回 `recordId`

#### POST `/api/qa/ask`

响应新增字段：

```json
{
  "recordId": 1001,
  "answered": true,
  "answer": "文档上传流程分为三个阶段...",
  "citations": []
}
```

#### POST `/api/qa/stream-ask`

流式接口在完成时新增一个 `record` 事件：

```text
event: record
data: {"recordId":1001}
```

事件顺序建议：

```text
token -> token -> ... -> citations -> record -> complete
```

如果为了简化前端，也可以把 `recordId` 合并进最后的 `citations` 事件，但语义不够清晰，不推荐。

### 6.2 历史列表

新增：

```http
GET /api/qa/records?groupId=1&page=1&pageSize=20&answered=true
```

查询规则：

- 普通用户默认只看自己的记录。
- Group Owner / Manager 可查询本群组记录。
- System Admin 可跨群组查询。

响应示例：

```json
{
  "success": true,
  "data": {
    "items": [
      {
        "id": 1001,
        "groupId": 1,
        "question": "文档上传流程是什么？",
```

## 7. 权限设计

沿用现有群组权限模型。

访问规则：

| 操作 | 权限 |
|---|---|
| 创建 QA 记录 | 当前用户必须对 `group_id` 有读权限 |
| 查询自己的 QA 历史 | 当前用户必须仍对该群组有读权限 |
| 查询群组 QA 历史 | Group Owner / Manager / System Admin |
| 查询 QA 详情 | 记录所有者，或该群组 Owner / Manager / System Admin |
| 删除 QA 记录 | 第一阶段不提供物理删除；后续可支持用户删除自己的展示记录 |

注意：

- 如果用户退出群组，默认不再允许查看该群组 QA 历史，以避免历史引用泄露。
- 审计或管理员统计可保留记录，但普通用户不可访问。

## 8. 与 `llm_usage_records` 的关系

当前 `llm_usage_records` 已记录 QA 的 token、耗时、模型和费用。

本阶段有两种选择：

### 方案 A：QA 记录冗余保存用量摘要

`qa_records` 保存 `prompt_tokens`、`completion_tokens`、`total_tokens`、`latency_ms`、`model_name`。

优点：

- QA 历史列表和质量看板查询简单。
- 不需要修改现有 `llm_usage_records` 表。

缺点：

- 用量数据在两张表中有轻微冗余。

### 方案 B：`llm_usage_records` 增加 `qa_record_id`

优点：

- 关系更规范，便于追踪一次 QA 的成本。

缺点：

- 需要改造 metrics 模块 DTO、Mapper 和插入逻辑。
- 流式接口中 record 和 usage 的生成顺序需要协调。

推荐：**第一阶段采用方案 A**。后续质量看板需要更精确成本归因时，再补 `qa_record_id` 外键。

## 9. 前端设计

### 9.1 当前问题

`useQaSessions.ts` 当前使用内存态 `sessions`：

```ts
const sessions = ref<QaSession[]>([])
```

这适合即时展示，但刷新后丢失，也不能跨设备查看。

### 9.2 调整方向

第一阶段前端可以保留当前本地会话体验，同时新增服务端历史能力：

- 提问成功后接收 `recordId` 并写入当前消息。
- QA 侧边栏新增“历史记录”或把当前本地 session 替换为服务端记录列表。
- 点击历史记录时调用 `GET /api/qa/records/{id}` 加载详情。

推荐演进：

1. 后端先完成记录落库和历史接口。
2. 前端保留现有临时会话，先在回答对象上保存 `recordId`。
3. 再把侧边栏历史切换为服务端分页列表。

这样风险最低，不会一次性重写 QA 页面的交互。

## 10. 异常与边界

### 10.1 业务拒答

业务拒答应保存为：

- `success=true`
- `answered=false`
- `reason_code=INSUFFICIENT_EVIDENCE` 或模型返回的拒答原因
- `answer=null`
- `citation_count=0` 或实际证据数量

### 10.2 模型格式错误

格式错误应保存为：

- `success=true`
- `answered=false`
- `reason_code=ANSWER_FORMAT_ERROR`
- `reason_message=模型返回格式错误，无法解析回答`

### 10.3 系统异常

系统异常应尽量保存：

- `success=false`
- `answered=false`
- `reason_code=SYSTEM_ERROR`
- `error_message=异常摘要`

如果异常发生在权限校验前，不应落库，因为尚未确认用户对群组有访问权限。

### 10.4 持久化失败

QA 持久化失败不应影响正常问答返回。

建议：

- 捕获落库异常。
- 写 warn/error 日志。
- 正常返回 `AskQuestionResponse`，但 `recordId=null`。

原因：用户问答结果比历史记录更关键，持久化失败不应破坏主链路。

## 11. 实施顺序

建议分四步实现：

1. **数据库和基础模型**
   - 新增 `qa_records`、`qa_record_citations`。
   - 新增 Entity、Mapper 和 XML。

2. **同步 QA 落库**
   - 扩展 `AskQuestionResponse.recordId`。
   - 扩展 `QaChatService.AskResult.evidenceLevel`。
   - 在 `QaService.ask` 中调用持久化服务。

3. **历史查询接口**
   - 新增 `QaRecordController`。
   - 实现列表和详情查询。
   - 接入权限校验。

4. **流式 QA 落库**
   - 累积 token。
   - 完成后保存 answer、citations、usage。
   - SSE 增加 `record` 事件。

## 12. 测试建议

### 12.1 单元测试

- `QaRecordPersistenceService`：
  - 成功回答落库。
  - 拒答落库。
  - citation 批量落库。
  - 持久化异常不影响主响应。

- `QaService`：
  - 同步问答返回 `recordId`。
  - 无证据拒答也会保存记录。

### 12.2 接口测试

- `POST /api/qa/ask` 返回 `recordId`。
- `GET /api/qa/records` 只能看到有权限的数据。
- `GET /api/qa/records/{id}` 返回 citations。
- 非群组成员无法查询记录。

### 12.3 流式测试

- 正常流式问答完成后保存完整 answer。
- 流式无证据时保存拒答记录。
- 流式异常时保存失败记录或至少不影响 SSE error 返回。

## 13. 验收标准

- 每次 `/api/qa/ask` 调用成功完成后产生一条 `qa_records`。
- 有引用的回答会产生对应 `qa_record_citations`。
- 拒答记录也会被保存。
- `AskQuestionResponse` 返回 `recordId`。
- QA 历史列表支持按用户和群组查询。
- QA 历史详情能回看问题、回答、拒答原因和引用。
- 普通用户不能查看无权限群组或他人的 QA 历史。
- 持久化失败不影响问答主流程。
- 当前 Assistant 模块不受影响。

## 14. 后续扩展

该设计完成后，可以自然支撑：

- 答案反馈：新增 `qa_answer_feedbacks`，通过 `qa_record_id` 关联。
- 知识库质量看板：基于 `qa_records` 和 `qa_record_citations` 聚合统计。
